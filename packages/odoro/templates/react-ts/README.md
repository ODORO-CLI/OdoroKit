# Odoro — single-page application

Project generated by `odoro create`. The router, the motion engine, the style
system and the interface components all come from `@odoro-cli/libs`; the
development server and the build come from the `odoro` engine.

## Structure

```
index.html          Document and entry point: the <script type="module"> tag
                    names the file to build.
odoro.config.ts     Engine configuration: aliases, port, proxy, build.
.env.example        The expected variables. Copy to `.env`, never committed.
public/             Files copied as-is to the root of the site.
src/
  main.tsx          React mounting and stylesheet imports.
  App.tsx           The whole page: nav, sections, footer.
  router.tsx        The route table — the only file that names the router.
  entry-server.tsx  Prerendering: which routes, and what they put in the head.
  background.tsx    The decorative background — the only piece tied to the
                    graphics engine.
  styles.css        Project styles and token overrides.
  odoro-env.d.ts    Ambient types (import.meta.env, asset imports).
```

## Scripts

| Command     | Effect                                          |
| ----------- | ----------------------------------------------- |
| `dev`       | Development server with hot reloading.          |
| `build`     | Production build into `dist/`.                  |
| `preview`   | Serves `dist/` the way a static host would.     |
| `typecheck` | Type checking, without emitting.                |

## Environment variables

Copy `.env.example` to `.env`. The files are read from the least specific to
the most specific — `.env`, `.env.local`, `.env.<mode>`, `.env.<mode>.local` —
and a variable already set in the environment is never overwritten by a file:
whatever your host injects wins.

**Only variables prefixed with `ODORO_` reach the browser**, through
`import.meta.env`. Anyone who opens the site can then read them. Everything
else stays on the machine.

```ts
const api = import.meta.env.ODORO_API
```

`odoro build --mode staging` reads `.env.staging` and fills in
`import.meta.env.MODE`.

## Prerendering

`build.prerender` is on: `odoro build` renders every route of
`src/entry-server.tsx` as a complete HTML document, and `main.tsx` hydrates it
on load rather than rebuilding everything.

That is what lets a search engine, a link preview or a screen reader find text
in the very first response. `/about` becomes `dist/about/index.html`, which any
static host serves with no configuration — nothing runs in production.

Adding a route: one line in `routes`, and the matching entry in
`src/router.tsx`. Doing without: remove `prerender` from `odoro.config.ts`,
then delete `src/entry-server.tsx`.

## Customising

Every visual value goes through a CSS variable. Overriding
`--o-palette-brand-600` in `src/styles.css` rethemes the application **and**
the library components, without touching their code.

A single stylesheet: `@odoro-cli/libs/styles.css`, imported once at the root of
the application.

It carries only the base — variables, preflight, animations. The utilities are
produced at build time, for the classes your code actually uses: a few tens of
kilobytes in practice, with the whole palette available and nothing weighing it
down.

## Hot reloading

Editing a component swaps its code without unmounting the tree: the value of a
counter, the text typed into a field, the open tab all survive the edit. A
stylesheet is swapped with no reload at all.

A module that exports more than components reloads the page, and that is
correct: nothing would let its change propagate safely.
